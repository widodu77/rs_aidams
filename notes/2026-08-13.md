# 2026-08-13 — Phase D/E: the sweep is flat, and λ is mathematically inert

The λ sweep completed and was evaluated on the held-out split. The result is a null: no gating at
any λ, and no response to λ at all. The reason turned out to be exact rather than statistical, and
it is the most useful thing this project has produced so far.

## The frontier

Held-out eval split, n=248, greedy decoding, fp16 throughout. Trained policies evaluated through
`generate.run_vllm --adapter`, i.e. the same pipeline that produced the fixed-policy baselines.

| policy | accuracy | tokens | think rate |
|---|---|---|---|
| never | 71.4% | 51 | 0.0% |
| always | 89.5% | 264 | 98.4% |
| adaptive prompt | 89.1% | 281 | 96.8% |
| trained λ=0.05 | 89.1% | 239 | 98.8% |
| trained λ=0.25 | 88.3% | 231 | 99.6% |
| trained λ=0.5 | 89.1% | 224 | 98.4% |
| trained λ=1.0 | 88.7% | 231 | 98.8% |
| trained λ=2.0 | 89.1% | 235 | 99.2% |
| **per-item oracle (bound)** | **92.7%** | **99** | — |

Two failures, and they are separate:

1. **No gating.** Think-rate is 98–100% at every λ, including 2.0. The break-even prediction —
   that thinking should switch off in the order `simple_python`, `multiple`, parallel categories,
   `irrelevance` — is cleanly falsified. The per-category think-rate table is a wall of ~100%.
2. **No λ response.** Tokens run 239, 231, 224, 231, 235 across a **40x** change in λ. That is
   noise around 230, not a trend.

There *is* a consistent ~17% token reduction against the adaptive prompt (231 vs 281) at equal
accuracy, replicated across all five runs, and it is distribution-wide rather than tail-only
(median 227 -> ~180, p90 509 -> ~400, truncation 3.2% -> ~1%). But it is identical at λ=0.05 and
λ=2.0, so it is not λ doing it.

## The finding: group-normalised advantage cancels λ exactly

The first explanation reached for was exploration failure — that no-think rollouts are never
sampled, so the reward cannot price a choice the model never makes. That is true, and it explains
the *gating* failure. **It does not explain the λ non-response**, because think-length varied
inside every group; λ had a live gradient the whole time.

The actual mechanism is arithmetic. On an all-correct group, correctness and format are constant,
so

```
reward = const - λ · (think_tokens / 768)
```

GRPO forms `advantage = (r - mean(r)) / std(r)`, and with `scale_rewards="group"` (TRL's default)
that `std` is itself exactly `λ · std(think_tokens) / 768`. **λ appears in both numerator and
denominator and divides out.** The advantage is bit-for-bit the same at λ=0.05 and λ=2.0.

Confirmed against the logged `reward_std` at step 5 of each run — a step where all eight rollouts
were correct, so length is the only source of variance:

| λ | logged reward_std | λ·std(think)/768 | ratio |
|---|---|---|---|
| 0.05 | 0.001068 | 0.001068 | 1.0003 |
| 0.25 | 0.005095 | 0.005094 | 1.0001 |
| 0.50 | 0.010290 | 0.010293 | 0.9997 |
| 1.00 | 0.021320 | 0.021315 | 1.0002 |

Four significant figures, four independent runs. This is not an inference from the null result; it
is a derivation the null result happens to confirm.

**Consequence: the sweep as designed could not have produced a Pareto curve** — not with more
steps, not with more compute, not with better hyperparameters. λ was never connected to the
gradient on the groups where it was the only signal.

**Why this generalises.** `scale_rewards="group"` is TRL's default and is there for good reason —
it stabilises GRPO. But it silently renders any *uniform* weight on a reward component inert
whenever that component is the sole source of within-group variance. Nothing warns you, and the
symptom is a flat sweep that reads as "the method does not work" rather than "the knob is not
connected". Any composite-reward GRPO setup is exposed to this.

## The second failure: GRPO cannot reinforce what it never samples

The gating failure has its own cause. Think-rate during training sat at ~99%, so a no-think
rollout essentially never entered a group. Advantage is computed *within* a group; if all eight
rollouts reason, the comparison "reason vs do not" is never made, and no λ can price an action
absent from the data.

The arithmetic is consistent with this rather than against it. At λ=0.5 the penalty is ~0.10 while
skipping reasoning costs ~0.18 of accuracy on this eval set, so continuing to think is *correct*.
By λ=2.0 the penalty (~0.39) should win — but by then there is no no-think mode left in the
sampling distribution to find.

**The proposal already specified the fix, and the implementation diverged from it.** The README
says: *"During training it samples both a reasoned and a direct continuation for the same input,
and the reward decides which one paid off."* What was implemented samples eight free continuations
and assumes both modes appear. They do not.

There is reason to expect forced pairing to work rather than merely to change the failure: the
oracle analysis found 866 of 1240 items where *both* policies are correct. On that majority, a
paired group presents two correct rollouts differing only in length, which is exactly the clean
"shorter wins" signal the gate needs.

## Two failures — which turned out to be one

The first reading was that these were independent problems needing independent fixes:

| failure | cause | proposed fix |
|---|---|---|
| λ has no effect | group-std normalisation cancels it | `scale_rewards` — one config line |
| policy never gates | no-think rollouts never sampled | paired rollouts (custom `rollout_func`) |

**The `scale_rewards` half was tested and does not work.** Two 60-step runs at λ=1.0:

**`batch` is a no-op here.** Step 1 gave loss 0.2406 / grad_norm 1.246 against `group`'s
0.2406 / 1.245 — identical. The reason is the batch geometry: `per_device 4 × accum 2 = 8 =
num_generations`, so there is exactly **one group per batch**, and batch-normalising a single
group *is* group-normalising. The flag cannot do anything until a step contains ≥2 prompts.

**`none` connects λ but the signal is negligible.** Gradient norms fall 10–30x
(`group`: 1.245, 0.531, 0.398, 1.381, 0.794 … versus `none`: 0.427, 0.170, 0.206, 0.192, 0.019 …),
and on all-correct groups the loss is literally ~1e-5 (`-6.7e-05`, `5.5e-05`, `-3.0e-05`). λ is in
the gradient and the gradient is nothing. This was the caveat flagged before running it, and it
held.

**The finding: paired rollouts fix both problems, so there is only one fix.**

This is the non-obvious part. Once a group contains both modes, reward differences come from
correctness (~0.18 on this eval set) *and* length (~λ·0.2). λ therefore changes **which rollout
ranks highest**, not merely the spread of an otherwise fixed ordering. Group normalisation divides
out a uniform *scale*; it cannot divide out a change of *ordering*. The cancellation derived above
holds only in the degenerate case where length is the sole source of within-group variance — which
is exactly the case unpaired sampling produces.

So `scale_rewards` stays at TRL's default, and the whole repair is the rollout mechanism the
proposal specified in the first place.

## Status of the project's claims

This is outcome 2 of the three named in the proposal: *"The policy collapses to always or never —
the reward cannot sustain a gate."* That was always a reportable result. But it should now be
reported with its cause attached, and the cause is not "GRPO cannot learn this" — it is two
specific, identified, fixable implementation facts. Reporting the null without the diagnosis would
be the weaker paper *and* the less true one.

What holds regardless of what happens next:

- The fixed-policy frontier and the `multiple`/`simple` structure (2026-08-09)
- **Prompting cannot produce a gate** — the adaptive prompt reasons on 96.8% of items and costs
  more than always-think for the same accuracy
- The per-item oracle: 92.7% at 99 tokens against always-think's 89.5% at 264, so the headroom is
  real and quantified
- The NF4-versus-fp16 sign flip (2026-08-09)
- λ-cancellation under group-normalised advantage, above

## Paired rollouts as implemented

`src/train/rollouts.py`, behind `--paired-rollouts`. Half of each group is rendered with
`enable_thinking=True` and half with `False`, so every group presents a real choice.

It reuses `trainer.vllm_generation.generate()` rather than driving vLLM directly. TRL's
`rollout_func` contract wants back `prompt_ids`, `completion_ids` and `logprobs`, and that method
returns exactly those — so sampling, weight syncing and logprob bookkeeping stay identical to the
standard path, and the only thing that differs is which chat template each half was rendered with.

Two implementation points worth recording:

**Prompts had to become conversational on this path.** The dataset stored pre-rendered strings,
and a string cannot be re-rendered with a different `enable_thinking` flag. `build_records` now
takes `conversational=True` for the paired path only; the standard path keeps its single
prompt-construction route, byte-identical to the baselines.

**`enable_thinking=False` prices the direct rollout correctly for free.** Qwen3's template closes
an empty `<think></think>` inside the *prompt*, so the completion begins outside the block. The
parser reports `did_think=False` and the reward charges zero think tokens — no special-casing
needed anywhere in the reward.

**The failure mode the tests exist for is silent.** TRL identifies a GRPO group by *consecutive
positions* in the returned batch. An off-by-one in the interleaving computes advantages across
rollouts belonging to different prompts — no exception, no shape mismatch, just a quietly wrong
gradient. Nine tests pin group contiguity, prompt purity, field alignment, the split sizes, and
that both template variants are actually requested.

## Bringing paired rollouts up (five failures, one cause)

The implementation took five attempts on Colab before a step completed. Recorded in full as
engineering log entries 23–27; the pattern is worth stating here because it is a methods-section
point, not a debugging anecdote.

| # | Surface error | Actual cause |
|---|---|---|
| 23 | reward fn got a list, not a string | conversational prompts changed the *completion* type |
| 24 | `'>' not supported between 'str' and 'int'`, inside vLLM | transformers v5 returns a `BatchEncoding` from `apply_chat_template` |
| 25 | `produced 16 completions, expected 64` | ~~`generate()` ignores `num_generations`~~ **wrong — see 27** |
| 26 | `tensor a (64) vs tensor b (361)`, inside the trainer | vLLM's top-k logprobs must be reduced to top-1 |
| 27 | `returned 64 rewards, but 8 were expected` | **prompts arrive pre-repeated `num_generations` times** |

Entries 25–27 are one bug, not three. TRL's sampler is built with
`RepeatSampler(mini_repeat_count=num_generations)`, so each item is already duplicated before
`rollout_func` sees it; I read the batch as distinct prompts and returned `num_generations` times
too many completions. Each fix corrected the error in front of it and carried the same wrong
assumption one layer deeper, where it reappeared as a different-looking failure. **The tell was
visible from the second failure: 16, 64 and 8 all differ by exactly the factor `num_generations`.**
When consecutive errors are off by the same factor, stop fixing errors and go verify the quantity
that factor names.

The umbrella lesson, covering all five: **overriding `rollout_func` means inheriting every
undocumented normalisation the default path performed** — and every property of the input it was
built to receive. TRL documents the hook by the dict it returns, while `_generate_single_turn`
quietly reduces logprobs and `_get_train_sampler` quietly duplicates prompts. Twenty lines of the
latter, which carries an ASCII diagram of exactly this batch layout in a comment, would have
prevented three of the five. *When replacing a hook, the default implementation and the code
constructing its inputs are the contract; the docstring is not.*

The fix, once the contract was right, made the module smaller: mode is now a property of a row's
position within its group, one `generate` call covers both modes, and the interleaving machinery is
gone.

Two secondary observations, both cheap and both earned the hard way:

- **The test suite was green at every one of the five failures**, because every test fed *unique*
  prompts and a fake built from my own assumptions. It encoded the misunderstanding faithfully. Each
  fix has since required making the fake *less* convenient — real types (24), realistic 3-D logprobs
  and mode-dependent lengths (26), pre-repeated prompt batches and a stride assertion (27). A fake
  built from your assumptions tests your assumptions, not your code. Suite now at 84.
- `FileNotFoundError: log_history.json` appeared in all five failures and was the cause of none.
  It is written after `train()` returns, so its absence restates the failure rather than explaining
  it. Cost real time twice before that registered.
