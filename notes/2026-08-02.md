# 2026-08-02 — Phase A: per-sample BFCL scoring

## Goal

Establish whether a single model output can be scored programmatically in isolation. Everything downstream depends on this: the evaluator *is* the GRPO reward function, so no training is possible until `score(prediction, ground_truth) -> float` exists.

## Findings

**The anticipated obstacle was wrong.** I expected BFCL's checker to be batch-CLI-only and to need reimplementing for per-sample use. It isn't: `ast_checker()` already takes a single prediction and returns `{"valid", "error", "error_type"}`. This is a meaningful de-risking — the official checker can serve as the reward directly, so reported numbers stay leaderboard-comparable.

**Friction 1 — import coupling.** Importing the checker triggers:

```
ast_checker → MODEL_CONFIG_MAPPING → every API model handler → qwen_agent → soundfile
```

A missing audio library blocks a pure-string AST checker. The whole chain resolves exactly one boolean, `underscore_to_dot`, which rewrites `.` → `_` in function names for providers (OpenAI, Mistral, Google) whose APIs reject dots. Worked around by pinning `CHECKER_MODEL_NAME = "gorilla-openfunctions-v2"` (flag is False → names compared verbatim). **Risk noted:** this fragile chain has to survive the Colab environment too.

**Friction 2 — decode is the real work.** The checker expects `{"func_name": {arg: value}}`; the model emits `{"name": ..., "arguments": {...}}`. The shape conversion plus `<think>` separation is what actually had to be written.

**Data schema.** Ground truth is `{func_name: {param: [acceptable_values...]}}` — a list of acceptable values per parameter, where `""` marks the parameter optional. So BFCL already permits multiple valid answers per item.

**Design point that nearly became a bug.** `format_ok` initially conflated "emitted malformed JSON" with "emitted no call at all". These must stay separate: on irrelevance items, zero calls is the *correct* answer. Whether "no call" is right or wrong is category-dependent and belongs to the scorer, not the parser. Split into `format_ok` (nothing malformed) and `has_calls`.

## Verification

Scorer discriminates correctly across: correct call (with and without reasoning), wrong argument value, wrong function name, missing required parameter, hallucinated parameter, wrong argument type, wrong call count, malformed JSON, prose-only output, correct abstention on irrelevance, and spurious call on irrelevance.

Also noted: `ast_checker` leaves a stale `error_type` populated even when `valid=True` — never branch on `error_type` without checking `valid` first.

## Full-dataset sweep (Phase A completion)

Switched the environment to uv (`uv sync` / `uv run pytest`), pinned in `uv.lock` — committed deliberately, since reproducibility is graded. Dropped the earlier standalone venv.

Hand-written tests only exercise paths I thought to test, so I ran the stronger check: score all 1000 single-turn items using a prediction reconstructed from each item's own ground truth. Anything below 100% means either the scorer or the reconstruction is wrong.

Started at **98.4%**. Every failure turned out to be a defect in my reconstruction helper, not the scorer — the scorer was correctly rejecting malformed input, which is the outcome I wanted. Three undocumented encoding rules in the BFCL ground-truth format had to be discovered by reading checker errors:

1. **Optional parameters should be omitted, not filled.** BFCL ground truth sometimes lists optional parameters that don't exist in the function schema at all (e.g. `permeability` on `calculate_voltage_difference`), so supplying them raises `unexpected_param`.
2. **`""` is not a reliable optionality marker.** It also appears on parameters the schema lists as *required* — `"formatted": [true, ""]` with `required: ["number", "formatted"]`. The schema's `required` list is the authority, not the ground truth. Getting this wrong traded one error class for another (98.8% → 99.2%, `unexpected_param` → `missing_required`).
3. **Acceptable-value lists nest through lists as well as dicts.** `"conditions": [[{"field": ["age"], ...}, ...]]` is a list *of dicts*, each carrying its own acceptable-value lists. Recursing into dicts but not lists left the inner lists intact.

Final: **1000/1000 across `simple_python`, `multiple`, `parallel`, `parallel_multiple`.** Retained as a parametrized regression test — if `bfcl-eval` is ever bumped and the encoding shifts, it fails loudly instead of silently corrupting every reward.

Suite now 25 tests, all passing. Two properties confirmed rather than assumed: parallel scoring is order-independent, and correctness is invariant to whether the model reasoned. The second is the invariant the project rests on — if the `<think>` block leaked into correctness, the length penalty would stop being the only pressure on the thinking decision.

**Phase A complete.**

## Phase B start — environment and output contract

**Hardware.** RTX 3050 Laptop, 4 GB VRAM (~3.4 GB free, ~900 MB always in use by the desktop), 15.3 GB RAM, driver CUDA 13.3. Verdict: Phase B inference runs locally; Phase D GRPO training does not fit in 4 GB and will need Colab. Decided to keep all logic in repo scripts rather than notebooks, and to split generation (GPU, writes JSONL) from scoring (CPU, reads JSONL) — so the Colab step later is one command and all iteration stays local.

**Environment.** Moved the uv environment out of OneDrive via `UV_PROJECT_ENVIRONMENT=C:/Users/walid/venvs/aidams-rs` — a ~2.5 GB CUDA install inside a synced folder would churn OneDrive badly.

Two CUDA setup traps, both worth remembering:

1. `[tool.uv.sources]` only overrides **direct** dependencies. torch arrives transitively via `bfcl-eval`, so the PyTorch index was silently ignored and a CPU build stayed pinned. Verified by grepping `uv.lock` for the torch source — `registry = "pypi.org"` gave it away. Fixed by declaring `torch` explicitly in `[project.dependencies]`.
2. cu128 has no Windows wheel above `torch 2.11.0`; `bfcl-eval` wants 2.13.0. Moved to the cu130 index, which resolves `2.13.0+cu130`. Confirmed working: `cuda available: True`, matmul on device.

**Output contract.** Written in `src/prompts/contract.py`. Identical parse format across policies, with only the reasoning instruction varying, so the scorer stays blind to which policy produced an output. Includes an explicit licence to abstain — without it a model told to call functions calls one on every input and the irrelevance category collapses to 0% for both policies.

**Finding: Qwen2.5 does not close its tool-call tag.** The first smoke run produced three perfectly correct calls that all scored 0.0. `<tool_call>` and `</tool_call>` are single added tokens in Qwen2.5's vocabulary (151657 / 151658) from its native tool-calling format, and the model emits the opening token plus the JSON, then goes straight to `<|im_end|>` without ever emitting the closing token. Not truncation — completions were 19–26 tokens against a 128 limit — and not special-token stripping, confirmed by decoding with `skip_special_tokens=False`.

Made the closing tag optional, parsing the JSON with `raw_decode` instead of matching a closing delimiter. This is a real design decision, not a convenience: requiring the tag would make the baselines measure Qwen's tag-emission habits rather than the effect of reasoning on correctness, confounding the exact comparison the project exists to make. Leniency stops at the tag — malformed JSON still fails, so `format_ok` keeps its meaning for the Phase C reward. Four tests added to pin the boundary. Suite now 29 tests; the 1000/1000 sweep still passes, so the change regressed nothing.

Same three smoke outputs now score 3/3. Generate → parse → score is proven end to end on local hardware.

Also noted: `<think>` / `</think>` are *not* single tokens in Qwen2.5 (3 tokens each). Relevant when counting think-tokens for the length penalty.

## Blocker: Qwen2.5-1.5B cannot reason and call in the same turn

4-bit NF4 works — Qwen2.5-1.5B loads in **1.15 GB**, comfortable on the 3050. The `never` policy is fine. The `always` policy is not, and three successive fixes each revealed the next layer:

1. **Weak instruction.** With "reason inside a `<think>` block", the model either answered in prose without calling anything (triangle area computed directly, no call) or wrote `think:` as prose. Strengthened the contract with an explicit "never compute the answer yourself" rule and a literal shape example.
2. **Still prose.** The model wrote `think` / `think:` / `think:` on all four items, never the literal tag. Cause traces to the earlier tokenizer finding: `<think>` is **not** in Qwen2.5's vocabulary (3 tokens), and Qwen2.5-Instruct was never trained to emit it — that convention arrived with Qwen3/QwQ. Prefilled the opening tag instead, which is faithful for a policy defined as "always think".
3. **Prefill worked, then the model stopped.** `<think>` blocks now form perfectly on 4/4 — and the model closes `</think>` and immediately emits `<|im_end|>`, never reaching the call.

Tested whether a second pass rescues it: fed the model its own completed `<think>...</think>` back and let it continue freely. **Empty continuation on all four.** Once `</think>` is in context the turn is over as far as the model is concerned.

Conclusion: this is a property of the base model, not the prompt. Qwen2.5-1.5B-Instruct does one thing per turn — it reasons, or it calls, not both. Forcing a call with a `<tool_call>` prefill would work but would make the `always` policy call on every irrelevance item by construction, destroying the most informative category with an artifact.

**Qwen3-1.7B is the fix.** `<think>` (151667) and `</think>` (151668) are native single tokens alongside `<tool_call>` (151657), and it has an explicit hybrid thinking / non-thinking mode — the exact structure this project studies. Still ≤2B, so the proposal's size constraint holds, and risk register item 3 already anticipates a base-model swap.

Worth noting this reframes the base-model choice as a substantive design decision rather than an arbitrary one: a project about *when to think* needs a model that can represent thinking at all.

## Qwen3-1.7B adopted — reason-then-call works

Replaced the prefill mechanism with Qwen3's `enable_thinking` chat-template flag, which maps directly onto the two fixed policies (`True` for always, `False` for never) and leaves the Phase D policy free to choose.

Smoke results on `simple_python`:

- **never** — 4/4 correct, `think=False`, clean calls at 20–34 tokens
- **always** — 2/2 correct, well-formed `<think>` block *followed by* the tool call, 145–156 tokens

The reason-then-call behaviour that Qwen2.5 could not produce at all works out of the box. Base-model switch validated.

One parser fix required: with `enable_thinking=False` Qwen3's template emits an empty `<think></think>`, which the parser would have counted as reasoning and reported the never-policy as thinking on every item. Empty blocks now resolve to "no thinking".

**Throughput.** 4-bit NF4, 1.35 GB VRAM. Batch 16 gives ~0.34 s/step; batch 32 is *worse* (1.33 s/step — superlinear, memory bandwidth saturating on a 4 GB card), and batch 2 is worse again. Batch 16 it is.

**Generation cap.** At 512 tokens, 3/16 items on `parallel_multiple` were truncated mid-reasoning and produced no call. That matters: an arbitrary cap would manufacture the "thinking hurts accuracy" result this project is supposed to *test*. Raised to 768 (>2× the 325-token median) and truncation rate is now reported as an explicit metric, so cap-driven failures stay visible rather than being absorbed into the accuracy number.

Qwen3 does visibly ramble on hard items ("Wait, but the user is asking...", "Wait, the first term is 0, so 13 terms? Let me count"). Whether that costs accuracy is exactly the question — it just has to be measured, not induced.

**Baseline run launched.** 100 items per category across all five categories, both policies, batch 16, cap 768. Analysis script `src/analysis/score_run.py` written while it runs: per-policy per-category accuracy and token cost, plus think-rate, truncation rate and no-call rate as artefact diagnostics.
