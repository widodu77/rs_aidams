## The training configuration, and why it is shaped this way

Working shape on a free-tier T4 (15 GiB):

```
--use-vllm --vllm-sleep --num-generations 8
--per-device-batch-size 2 --gradient-accumulation-steps 4
--max-completion-length 768 --temperature 1.2
```

Three of those are not defaults but forced choices, each measured rather than guessed:

**vLLM for rollouts.** With HF `generate` a step cost ~15 min, i.e. ~75 h for a 300-step run — the
same static-batching problem that cost 2.36x during baseline generation, now inside a loop that
runs hundreds of times. vLLM's continuous batching brings it to ~85 s/step.

**Forward batch 2, group 8.** Peak memory is dominated not by activations (gradient checkpointing
handles those) but by the **logits tensor**: GRPO needs per-token log-probabilities, so the forward
materialises `batch x completion_tokens x vocab`. With Qwen3's 151936-token vocabulary that is
~1.9 GiB at batch 8, computed twice per step (policy and reference). Splitting the forward while
keeping the GRPO group at 8 via gradient accumulation cuts it to ~0.5 GiB. Worth stating plainly
because it is counter-intuitive: **for RL on language models peak memory scales with vocabulary
size, not parameter count.**

**Temperature 1.2, not 1.0.** The first full run logged entropy at 0.05–0.13. Low rollout diversity
means rollouts agree, which means zero advantage and no gradient. Raising temperature is the
cheapest lever on that, and it affects training only — evaluation stays greedy, matching how the
fixed-policy baselines were generated, so nothing about comparability changes.

Throughput: **~85 s/step**, tracking completion length closely (38 s at a 190-token mean, 125 s at
476). 50 steps ≈ 73 min.

## The go/no-go gate: 50 steps at lambda = 0

The proposal specifies this gate as *"train on correctness reward only, no length penalty. Does
accuracy improve over base? If GRPO cannot improve plain correctness on this model, the adaptive
question is moot."*

Result: **37 of 50 steps produced no gradient at all.**

| | |
|---|---|
| steps with `frac_reward_zero_std = 1.0` | 37/50 (74%) |
| think-rate | 1.000 on 23 of the 25 logged rows |
| entropy | 0.057 – 0.200 |
| truncation | 0% on all but two logged steps |

Every dead step has the identical signature: `correct 1.000`, `format 1.000`, `reward 1.200`. All
eight rollouts were right, so the group had zero variance.

**This is arithmetic, not a bug.** At lambda = 0 the reward is `correct + 0.2 x format`, which takes
about four distinct values. A model already at 87.5% accuracy will have all eight rollouts agree on
most prompts. GRPO computes advantage *within* a group, so an all-correct group contributes exactly
nothing.

Incidentally this confirms the reward is computing as designed: 1.200 = 1.0 correctness + 0.2
format is precisely `w_correct=1.0, w_format=0.2, lambda=0`, verified in situ rather than only in
unit tests.

## Finding: a correctness-only reward cannot train a model that is already mostly correct

The gate as specified is **unanswerable on this task**, and the reason is structural rather than
incidental. This is worth stating as a finding rather than hiding as a deviation:

- The reward has too few distinct levels to separate eight rollouts.
- The base model is too good for those levels to be hit differently within a group.
- With one prompt per optimizer step, the 26% of steps that *did* carry signal are far too few and
  too noisy to move an 87.5%-accurate model in 50 steps.

There is also no correctness *trend* in the trace, and none should be read into it: with one prompt
per step, each row's `correct` mostly reports whether that particular prompt was easy.

**What the gate did establish**, which is narrower but real: the loop runs end to end, the reward
behaves exactly as specified, the metric instrumentation works, gradients flow whenever variance
exists, and a 50-step run completes in ~73 minutes on free-tier hardware.

**A second observation, unprompted:** think-rate sat at 1.000 on essentially every step. At
lambda = 0 reasoning is free, so nothing pushes against it. This is the "prompting cannot produce a
gate" result from the baselines reappearing *inside* training — the model will not stop reasoning
unless something charges it for reasoning. The length penalty is not a refinement of this project;
it is the entire mechanism.

## The mechanism that makes lambda > 0 work, and a falsifiable checkpoint

Look at `thinkTok` on the dead steps: 120, 165, 144, 200, 388, 333, 111, 157, 216, 319, 213, 125,
193, 231, 108, 254.

Those rollouts were **identical in reward and wildly different in length**. Any lambda > 0 prices
that difference, so every one of those dead groups becomes informative. And because GRPO normalises
advantage by group standard deviation, even small length differences produce order-1 advantages —
lambda does not merely add signal at the margin, it converts the majority of steps from dead to
live.

This yields a prediction that can be checked at the *first* point of the sweep rather than after
all of it:

> **At lambda = 0.05, the no-gradient rate should collapse from ~74% toward ~0%.**

The sweep loop prints `N/M steps with no gradient` after each run. If lambda = 0.05 does not drop
it sharply, the model of the reward above is wrong and the sweep should be stopped and rethought
rather than run for twelve hours on a false premise.

## Deviation from the proposal, and its justification

The proposal gates the whole project on correctness-only GRPO improving over base. That criterion
is retained in the record but cannot be met, for the structural reason above. Proceeding to the
lambda sweep is therefore a considered deviation, not a shortcut:

1. The gate's *mechanism* purpose — does the training loop work — is satisfied.
2. Its *scientific* purpose cannot be satisfied by any amount of compute at lambda = 0.
3. The question the project actually asks is about the cost-quality frontier, and the fp16 oracle
   already shows the prize is on the cost axis: 91.2% at 97 tokens against always-think's 87.3% at
   267. A policy that holds accuracy while cutting tokens is the target, and that is exactly what
   lambda trains for.

## Sweep plan

Five values x 100 steps, ~12 h total, spread across sessions:

`{0.05, 0.25, 0.5, 1.0, 2.0}` — covering every break-even transition computed from the fp16
baselines (`multiple` 0.07, `parallel` 0.48, `parallel_multiple` 0.53, `irrelevance` 2.11, with
`simple_python` never worth thinking at Δ = −2.8%).

Runs are checkpointed every 10 steps and resume from Drive, so a Colab disconnect costs minutes
rather than a lambda. This was added after an accidental interrupt killed a run at step 4 of 50.

Prediction to test alongside the Pareto curve: as lambda rises, thinking should switch off in
break-even order — `simple_python` first, then `multiple`, then the parallel categories, with
`irrelevance` last. That is falsifiable independently of where the curve lands, and it is the
bridge to H1.
